# YDP.Lab Project 종합 문서

> 이 문서는 Notion의 `YDP.Lab Project` 상위 페이지와 연결된 15개 하위 문서를 통합해 정리한 프로젝트 개요다. 문서마다 서로 다른 시점의 실험 코드와 초안이 섞여 있으므로, 현재 서비스의 최종 방향은 8개 군집·8개 동물 유형으로 정리하고 이전의 `k=5`, `k=6` 기록은 모델 발전 과정으로 구분했다.

## 1. 프로젝트 한눈에 보기

YDP.Lab Project는 여가생활 설문 응답을 바탕으로 사용자를 비슷한 생활 패턴의 군집으로 분류하고, 각 군집을 대표하는 동물 캐릭터와 해석 결과를 제공하는 웹 서비스다.

사용자는 소득, 여가 목적, 평일·주말 여가시간, 여가 사용 비율, 관심 여가활동 순위를 입력한다. 백엔드는 학습된 군집분석 파이프라인에 이 값을 넣어 군집 번호를 예측하고, 해당 군집에 매핑된 동물·유형명·분석 요약·주요 지표·이미지를 반환한다. 프론트엔드는 이 결과를 성격 유형 테스트처럼 시각화한다.

핵심 흐름은 다음과 같다.

```text
설문 문항 조회
  → 사용자 응답 및 입력값 검증
  → 14개 모델 입력 변수로 변환
  → 결측값 보정·표준화·PCA·K-Means 예측
  → 군집 번호를 8개 동물 유형에 매핑
  → 설명·근거 지표·특성 태그·이미지를 결과 화면에 표시
```

## 2. 서비스 목표와 결과물

### 목표

- 정형 설문 데이터를 사용해 사용자의 여가생활 패턴을 데이터 기반으로 분류한다.
- 숫자 군집을 친근한 동물 캐릭터로 변환해 분석 결과의 이해도와 흥미를 높인다.
- 단순 동물 추천을 넘어, 추천 근거가 되는 행동 특성과 주요 지표를 함께 보여준다.
- 행사·부스 체험에서도 짧은 설문 후 즉시 공유할 수 있는 결과를 제공한다.

### 주요 결과물

- 설문조사 웹 UI
- FastAPI 기반 질문 조회 및 분석 API
- scikit-learn 기반 군집분석 파이프라인
- 8개 군집별 동물·유형 설명 데이터
- 동물 SVG 정적 이미지
- Docker 이미지와 Hugging Face Spaces 배포
- GitHub Pages 기반 프론트 배포

## 3. 설문과 모델 입력 데이터

모델은 총 14개 값을 입력으로 사용한다.

| 영역 | API/모델 필드 | 내용 |
|---|---|---|
| 경제 배경 | `householdIncome` / `household_income` | 월 가구소득 구간 |
| 여가 목적 | `leisurePurpose` / `leisure_purpose` | 여가 사용 목적 1순위 |
| 여가 목적 | `leisurePurpose2` / `leisure_purpose_2` | 여가 사용 목적 2순위 |
| 시간 | `weekdayAvgLeisureTime` / `weekday_avg_leisure_time` | 평일 하루 평균 여가시간 |
| 시간 | `weekendAvgLeisureTime` / `weekend_avg_leisure_time` | 주말 하루 평균 여가시간 |
| 배분 비율 | `restRecreationRate` / `rest_recreation_rate` | 휴식·오락 비율 |
| 배분 비율 | `hobbyRate` / `hobby_rate` | 취미 비율 |
| 배분 비율 | `selfImprovementRate` / `self_improvement_rate` | 자기계발 비율 |
| 배분 비율 | `socialRelationshipRate` / `social_relationship_rate` | 대인관계·교제 비율 |
| 관심 활동 | `leisureActivity1`~`5` / `leisure_activity_1`~`5` | 관심 여가활동 1~5순위 |

### 선택 항목

가구소득은 무응답, 300만 원 미만, 300만~500만 원 미만, 500만~700만 원 미만, 700만 원 이상의 구간으로 구성된다.

여가 목적은 마음의 안정·휴식, 남는 시간 보내기, 가족·지인과 시간 보내기, 자기만족·즐거움, 자기계발, 스트레스 해소, 건강 관리, 대인관계·교제, 기타 중에서 1·2순위를 고른다.

관심 여가활동은 없음, 미디어/콘텐츠, 스포츠/운동, 여행/야외활동, 문화/예술, 자기계발, 사교/가족, 일상/휴식, 기타 중에서 1~5순위를 고른다.

### 입력 검증 규칙

- 휴식·오락, 취미, 자기계발, 대인관계·교제의 네 비율 합계는 반드시 100이어야 한다.
- 1순위와 2순위 등 순위형 질문에서 같은 선택지를 중복 선택하지 않도록 해야 한다.
- 프론트 배열 인덱스는 0부터 시작하지만 일부 원본 데이터 코드는 1부터 시작한다. 실제 구현 기록에서는 `leisurePurpose + 1` 보정이 필요했다.
- 프론트의 camelCase와 모델 학습 데이터의 snake_case를 명시적으로 변환해야 한다.
- 서버는 범위, 타입, 누락값을 재검증해야 한다. 클라이언트 검증만으로는 충분하지 않다.

## 4. 데이터 분석과 군집 모델

### 파이프라인

문서의 FastAPI 테스트 코드는 다음 scikit-learn 파이프라인을 사용한다.

1. `SimpleImputer(strategy="median")`: 결측값을 중앙값으로 보정한다.
2. `StandardScaler`: 서로 다른 척도의 수치 변수를 표준화한다.
3. `PCA(n_components=2)`: 데이터를 2차원 주성분 공간으로 축소한다.
4. `KMeans`: 축소된 공간에서 사용자를 군집에 배정한다.

재현성을 위해 `random_state=42`를 사용하고, 초기 실험 코드에서는 `n_init="auto"`를 사용했다. 학습 데이터 파일로는 `mz_processed.csv`가 기록되어 있다.

### PCA와 군집 수 실험

문서에는 여러 실험 단계가 공존한다.

| 단계 | 설정·결과 | 의미 |
|---|---|---|
| 초기 API 테스트 | `k=5`, PCA 2차원 | 입력부터 FastAPI 예측까지 연동을 검증한 실험 |
| 탐색 결과 | PCA 2차원, `k=2` 실루엣 약 0.364 | 분리도만 보면 가장 높은 단순 분할 |
| 비교 실험 | `k=6` 실루엣 약 0.358 | 분리도와 해석 가능한 세분화 사이의 절충안 |
| 비교 실험 | `k=8` 실루엣 약 0.328 | 군집 경계는 다소 약해지지만 8개 유형 콘텐츠 구성 가능 |
| 비교 실험 | `k=10` 실루엣 약 0.326 | 추가 세분화 대비 개선이 거의 없음 |
| 최종 콘텐츠 | 8개 군집·8개 동물 | 현재 문서상 서비스 결과 체계 |

PCA 스크리 플롯에서는 데이터 분산이 여러 성분에 고르게 퍼져 있어 소수 주성분만으로 전체 변동을 충분히 설명하기 어렵다는 판단이 기록되어 있다. 차원을 줄이지 않으면 실루엣 점수가 낮아졌고, 3차원 PCA 역시 2차원보다 전반적으로 낮은 점수를 보였다. 따라서 현재 방식은 순수한 통계적 최적화보다 서비스에서 이해할 수 있는 유형 수와 시각화 가능성을 함께 고려한 선택으로 보는 것이 적절하다.

### 군집을 가르는 핵심 축

- 휴식·오락에 쓰는 비율
- 취미와 자기계발 비율
- 평일·주말 여가시간
- 가구소득 구간
- 대인관계·교제 비율
- 관심 여가활동의 순위와 미참여(0) 비율

분석 기록에서는 `hobby_rate`와 `self_improvement_rate`, `rest_recreation_rate`와 `social_relationship_rate`, 후순위 관심 활동 변수들 사이의 상관도 관찰됐다. 일부 군집은 활동 변수의 0값이 매우 많으므로, 이를 실제 “무관심”과 결측·코딩상의 0으로 구분하는 것이 중요하다.

## 5. 최종 8개 군집과 동물 추천

아래 매핑은 최종 분석결과와 결과 응답 초안을 기준으로 통합했다.

| 군집 | 대표 유형 | 동물 | 핵심 성향 |
|---:|---|---|---|
| 0 | 위풍당당 | 범고래 | 건강 관리와 성장을 중시하고, 적은 여가도 스포츠·자기계발에 투자하는 주도형 |
| 1 | 고요한 탐험가 | 왜가리 | 스트레스 해소와 여행·자연 경험을 중시하며 익숙한 사람과 편안한 교류를 즐기는 유형 |
| 2 | 여유만만 | 매너티 | 휴식과 자기돌봄을 우선하고, 풍요롭고 느긋한 일상의 행복을 추구하는 유형 |
| 3 | 끈기의 비상가 | 알바트로스 | 여가시간은 짧지만 운동·여행·자기계발에 높은 밀도로 몰입하는 활동형 |
| 4 | 슬로 라이퍼 | 푸른바다거북 | 휴식·오락 비율이 매우 높고 혼자만의 안정적 재충전을 선호하는 독립형 |
| 5 | 에너자이저/소신파 | 돌고래 | 스포츠·야외활동과 관계를 즐기면서 미디어·휴식으로 에너지를 조절하는 유형 |
| 6 | 균형의 수호자 | 펭귄 | 시간과 소득 여유를 바탕으로 휴식·자기계발·관계를 고르게 조율하는 균형형 |
| 7 | 유유자적 | 해파리 | 여가시간이 가장 많고 휴식·오락에 크게 집중하며 저비용·저강도 활동을 선호하는 유형 |

### 군집별 해석 메모

#### Cluster 0 — 범고래

건강 관리와 자기 성장에 대한 의지가 강하다. 여가를 단순히 쉬는 시간이 아니라 운동, 취미, 자기계발과 관계를 통해 삶의 질을 높이는 투자로 본다. 문서에서는 “성장 지향 중활동형”으로도 표현됐다.

#### Cluster 1 — 왜가리

저소득·한정 참여형이라는 분석명도 사용됐으나, 최종 사용자용 설명은 조용한 환경과 여행·자연, 익숙한 사람과의 만남을 통한 스트레스 해소에 초점을 둔다. 참여 범위가 좁다는 데이터적 특징을 부정적으로 낙인찍지 않는 표현이 중요하다.

#### Cluster 2 — 매너티

휴식과 관계를 중시하며 자기돌봄과 느긋한 일상을 선호한다. 큰 모험이나 빠른 성취보다 커피, 독서, 공원, 여행 등 소소하고 확실한 행복으로 활력을 얻는 유형이다.

#### Cluster 3 — 알바트로스

평일과 주말의 여가시간이 모두 짧지만, 그 시간을 취미와 자기계발에 집중한다. 휴식과 사회관계 비율은 상대적으로 낮고, 운동·여행 같은 활동에서 성취와 활력을 얻는다.

#### Cluster 4 — 푸른바다거북

휴식·오락 비율이 약 84%로 8개 유형 중 가장 높고, 대인관계·교제 비율은 약 8.3%로 가장 낮다는 분석 예시가 있다. 여가 목적 1·2순위에서도 마음의 안정과 휴식이 높아 혼자만의 재충전을 선호하는 유형으로 해석했다.

#### Cluster 5 — 돌고래

소득과 여가시간이 비교적 높고 활동 비율이 고르게 분포한다. 스포츠·야외 활동으로 에너지를 높이고, 미디어·일상 휴식으로 회복하며, 대인관계 속에서 시너지를 얻는다. 문서에서 “중간 참여·균형형”, “소신파”, “에너자이저”라는 표현이 혼용되므로 최종 명칭을 하나로 확정할 필요가 있다.

#### Cluster 6 — 펭귄

고소득·시간 여유형으로, 특정 활동에 과도하게 치우치지 않는다. 휴식, 자기계발, 관계, 콘텐츠와 여행을 조화롭게 배치하는 성향이다. 문서상 프로파일링 경고가 가장 적고 데이터 규모도 큰 군집으로 기록됐다.

#### Cluster 7 — 해파리

평일 평균 약 5.56시간, 주말 평균 약 7.46시간으로 문서상 가장 긴 여가시간을 보인다. 반면 취미·자기계발·교제의 0 비율이 높고 휴식·오락 편중이 강하다. 사용자 설명에서는 “게으름”이나 “저소득” 같은 낙인보다 회복, 평화, 낮은 에너지 소비라는 긍정적 언어를 사용하는 편이 적절하다.

## 6. 백엔드와 API

### 기술 구성

- 서버 프레임워크: FastAPI
- 데이터·모델: pandas, NumPy, scikit-learn
- 요청·응답 검증: Pydantic
- 정적 파일: FastAPI `StaticFiles`
- 컨테이너: Docker
- 백엔드 배포: Hugging Face Spaces
- 프론트 배포: GitHub Pages

### `GET /questions`

프론트에서 표시할 질문 목록과 선택지를 반환한다. 현재 문서 초안은 서버에 `qslists` 배열을 하드코딩하고 그대로 반환하는 구조다.

```json
[
  {
    "title": "당신의 월 가구 소득 정도를 선택해주세요.",
    "choices": ["무응답", "300만원 미만", "300 이상 500만원 미만", "500 이상 700만원 미만", "700만원 이상"]
  }
]
```

### `POST /questions`

14개 설문 값을 받아 모델 입력 벡터로 만들고, `pipe.predict()`로 군집을 구한 다음 `result_classify(cluster)` 결과를 반환한다.

요청 예시는 다음과 같다.

```json
{
  "householdIncome": 0,
  "leisurePurpose": 1,
  "leisurePurpose2": 6,
  "weekdayAvgLeisureTime": 5,
  "weekendAvgLeisureTime": 10,
  "restRecreationRate": 95,
  "hobbyRate": 0,
  "selfImprovementRate": 0,
  "socialRelationshipRate": 5,
  "leisureActivity1": 1,
  "leisureActivity2": 7,
  "leisureActivity3": 1,
  "leisureActivity4": 7,
  "leisureActivity5": 6
}
```

### 결과 응답 구조

문서의 최신 초안을 정규화하면 다음 구조가 된다.

```json
{
  "animal": "푸른바다거북",
  "animalName": "당신의 동물은 푸른바다거북입니다.",
  "animalType": "슬로 라이퍼 푸른바다거북",
  "description": "결과 한줄 소개",
  "animalDescription": "대표 동물의 생태·행동 설명",
  "typeDescription": "사용자 군집의 종합 설명",
  "analSummary": [
    {"subtitle": "분석 키워드", "content": "결론과 근거"}
  ],
  "metrics": [
    {"subtitle": "지표명", "content": "군집 평균·전체 평균·순위 등 구체적 수치"}
  ],
  "clusterInfo": {
    "number": 4,
    "animal": "푸른바다거북",
    "type": "슬로 라이퍼"
  },
  "interesting": ["조용한 몰입", "감성 루틴", "휴식이 최고"],
  "animalImageUrl": "https://<backend>/static/animals/greenseaturtle.svg"
}
```

`analSummary`는 이해하기 쉬운 분석 결론과 근거를, `metrics`는 비교 범위가 명확한 수치를 제공한다. “평균”, “비율”, “1위” 같은 표현에는 반드시 해당 군집 기준인지 전체 응답자 기준인지 명시해야 한다.

## 7. 프론트엔드 결과 화면

결과 화면은 다음 순서로 구성하는 방향이 기록되어 있다.

1. 동물 이름과 캐치프레이즈
2. 한 줄 소개
3. 동물 이미지와 동물 특징
4. 동물 유형 소개(군집 종합평)
5. 분석 요약 카드 목록
6. 주요 지표 카드 목록
7. 직관적인 특성 태그

특성 태그는 해시태그 문구보다 “조용한 몰입”, “자기돌봄”, “균형의 미학”처럼 사용자가 바로 이해할 수 있는 표현을 지향한다. 태그도 실제 군집 데이터로 뒷받침되어야 한다.

## 8. 동물 이미지와 정적 파일 배포

동물 SVG는 백엔드의 `static/animals/` 아래에 두고 FastAPI에서 정적 경로로 공개한다.

```text
project/
├─ main.py
└─ static/
   ├─ logo.svg
   └─ animals/

      ├─ greyheron.svg
```

```python
app.mount("/static", StaticFiles(directory="static", html=False), name="static")
```

결과 API의 `animalImageUrl`은 `/static/animals/<filename>.svg` 형식의 절대 URL을 전달한다. 캐릭터 디자인은 귀엽고 친근한 만화풍, 단순하고 인상적인 형태, 각 군집의 여가 성향을 보여주는 소품과 배경을 공통 원칙으로 삼는다.

## 11. 문서 간 불일치와 기술 부채

### 모델 버전 불일치

테스트 코드에는 `k=5`, 별도 분석에는 `k=6`, 최종 결과 콘텐츠에는 `k=8`이 기록되어 있다. 운영 코드와 모델 아티팩트가 실제로 8개 군집을 사용하도록 고정됐는지 확인해야 한다. 모델 버전, 학습 데이터 버전, 입력 컬럼 순서를 함께 저장해야 재현할 수 있다.

### 모든 유형에 복사된 설명

`result_classify` V2 초안에서 여러 군집의 `typeDescriptoon`, `analSummary`, `metrics`가 푸른바다거북 예시로 동일하게 복사되어 있다. `분석결과` 페이지에 작성된 군집별 최종 문구로 교체됐는지 운영 코드를 확인해야 한다.

### API 필드 오탈자와 구조 문제

- `typeDescriptoon` → `typeDescription`
- `culsterInfo` → `clusterInfo`
- `clusterInfo`를 한 키짜리 객체 배열로 두기보다 하나의 객체로 만드는 편이 명확하다.
- `animalType`에서 돌고래가 “소신파”와 “에너자이저”로 혼용된다.
- 초기 응답 예시의 디버그 필드(`cluster`, `X_first_row`, `leisurePurpose_plus1`)는 운영 응답에서 제거하거나 개발 모드로 제한해야 한다.

### 범주형 데이터 처리

소득 구간, 여가 목적, 관심 활동은 숫자로 인코딩돼 있지만 본질적으로 범주형 또는 순서형 변수다. 단순 표준화와 PCA는 코드값 사이의 수치적 거리를 실제 의미로 취급할 수 있다. 현재 결과를 유지하더라도 원-핫 인코딩, 범주형 거리 기반 군집, Gower distance, k-prototypes 등의 대안과 안정성을 비교할 가치가 있다.

### 모델 학습 시점

예제 코드는 서버 시작 때 CSV를 읽고 매번 파이프라인을 학습한다. 운영 환경에서는 검증된 파이프라인을 별도 아티팩트로 저장하고 로드해야 시작 시간, 재현성, 배포 간 결과 일관성을 확보할 수 있다.

### 하드코딩된 콘텐츠

질문과 군집 결과가 Python 배열·조건문에 직접 들어 있다. 규모가 작을 때는 단순하지만 문구 수정과 다국어화, 실험 추적이 어렵다. JSON/YAML 설정이나 관리 가능한 데이터 저장소로 분리하고 스키마 검증을 적용하는 편이 좋다.

### 통계 표현의 신뢰성

군집별 문구에 포함된 백분율, 전체 평균, 순위는 모델과 데이터가 바뀌면 함께 갱신되어야 한다. 수동 작성 문구와 계산 결과가 어긋나지 않도록 지표를 코드에서 산출하거나 생성 시점을 기록해야 한다.

### 보안

Notion 상위 페이지에 Hugging Face 액세스 토큰으로 보이는 문자열이 평문으로 기록되어 있었다. 이 문서에는 값을 옮기지 않았다. 해당 토큰은 즉시 폐기·재발급하고, Notion 기록과 Git 이력에서 제거한 뒤 배포 플랫폼의 Secret 기능 또는 환경변수로 관리해야 한다.

## 12. 권장 다음 작업

우선순위가 높은 순서로 정리하면 다음과 같다.

1. 노출된 Hugging Face 토큰을 폐기하고 새 토큰을 Secret으로 등록한다.
2. 운영 모델의 최종 군집 수를 8로 확정하고 모델·데이터·입력 스키마 버전을 기록한다.
3. 8개 군집 모두에 고유한 `typeDescription`, `analSummary`, `metrics`가 들어가는지 테스트한다.
4. API 필드 오탈자를 바로잡고 Pydantic 응답 모델을 단일 계약으로 고정한다.
5. 14개 입력값의 범위, 비율 합계 100, 순위 중복, 누락값을 서버에서 검증한다.
6. 모델을 서버 시작 때 재학습하지 않고 검증된 아티팩트로 로드한다.
7. 범주형 변수 처리 방식과 군집 안정성을 재평가하고 결과를 기록한다.
8. 질문·결과 콘텐츠를 코드에서 분리하고 수정 가능한 데이터 파일로 관리한다.
9. 모델 예측, 인덱스 보정, 군집-동물 매핑, API 스키마에 자동화 테스트를 추가한다.
10. 사용자에게 “성격 진단”이 아니라 설문 패턴 기반의 재미·참고용 추천임을 안내한다.

## 13. 최종 정의

YDP.Lab은 여가생활 설문을 14개 특성 벡터로 변환하고, 전처리·PCA·K-Means를 통해 사용자를 8개 생활 유형 중 하나로 분류한 뒤, 그 결과를 범고래·왜가리·매너티·알바트로스·푸른바다거북·돌고래·펭귄·해파리 캐릭터로 설명하는 웹 기반 데이터 체험 서비스다. 기술적으로는 FastAPI와 scikit-learn을 Docker로 패키징해 Hugging Face Spaces에 배포하고, GitHub Pages 프론트엔드가 질문과 분석 결과를 API로 주고받는 구조다.

프로젝트의 강점은 통계적 군집을 친근한 결과 콘텐츠로 번역했다는 점이다. 앞으로의 핵심 과제는 최종 모델 버전과 API 계약을 고정하고, 군집별 문구와 지표를 실제 분석값에 맞게 자동으로 동기화하며, 노출된 비밀정보와 범주형 데이터 처리 문제를 정리하는 것이다.
